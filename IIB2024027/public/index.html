03 / UNDERSTAND THE FLAW

What is happening?

03
A

Vulnerable flow

User input↓String concatenation↓Shell interprets syntax↓Extra command output

The vulnerable endpoint adds input to a shell command. The shell treats ; as a command separator.

B

Protected flow

User input↓Argument array↓No shell interpretation↓Input printed as text

The protected endpoint passes the value as one argument to echo using execFile().

⌘

Root cause

Untrusted input is concatenated into a shell command. The shell interprets special characters in that input as command syntax, allowing an unintended command to execute.

04 / DEFEND THE APPLICATION

Mitigation and alternatives

04
DefenseHow it helpsIn this project
Avoid the shellUse a library or process API that does not interpret a shell command string.Implemented
Argument-vector executionPass the executable and its arguments separately instead of concatenating them into a command string.Implemented
Allow-list validationAccept only expected values, such as a valid IP address if an IP is required.Also used to restrict demo inputs
Least privilegeRun the application with only the operating-system permissions it needs.Alternative defense to explain

No single API makes every input safe automatically. Keep input validation, a fixed executable, timeouts, output limits, and least privilege.

VIVA QUICK ANSWER

How would you explain this project?

“My project demonstrates in-band OS command injection. The vulnerable endpoint concatenates a predefined user input into a shell command using exec(), so the shell runs the second harmless command and its output returns in the HTTP response. I mitigated this by using execFile() with a separate argument array, so the semicolon is treated as text rather than a command separator. I compare both outputs using the same payload.”
